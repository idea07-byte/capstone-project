1. Executive Summary & Abstract

The modern digital economy demands robust, high-performance, and resilient e-commerce architectures capable of seamlessly coordinating multi-party commerce. BuyIt is a full-featured, enterprise-grade Multi-Vendor E-Commerce Marketplace engineered as an end-to-end capstone software system. Modeled after premier platforms such as Amazon and Flipkart, BuyIt connects three distinct classes of users: Customers (storefront discovery, cart, wishlist, transactional checkout), Vendors (merchant storefront, product listing management, order fulfillment), and Administrators (platform governance, merchant verification, revenue tracking, category taxonomy).

From a systems engineering standpoint, BuyIt challenges modern software bloat by implementing an ultra-lean, high-throughput backend using pure Java SE (JDK 17+) with zero external application frameworks (no Spring Boot, Tomcat, or Jakarta EE overhead). Built atop the standard library's com.sun.net.httpserver.HttpServer, the backend incorporates a custom multi-threaded routing router, dynamic proxy-based JDBC connection pool, and an in-memory concurrent session manager. It operates alongside a state-of-the-art React 18 Single-Page Application (SPA) styled with glassmorphic modern CSS, and communicates with a cloud-hosted Supabase PostgreSQL relational database containing 15 normalized tables, 1,000 real products, and 3,000 product images across 15 consumer categories.

2. Introduction & Problem Formulation

2.1 Background & Motivation

Electronic commerce has transitioned from basic single-retailer portals into multi-vendor marketplaces where independent merchants maintain distinct catalogs, fulfill line items, and manage individual inventories under a unified platform umbrella. Building such platforms introduces complex distributed software challenges:

  • Catalog Diversity: Managing thousands of Stock Keeping Units (SKUs) across diverse taxonomies with multi-image representations.
  • Inventory Race Conditions: Preventing overselling when concurrent customers attempt to purchase the final units of a fast-depleting product.
  • Data Immutability: Preserving historical financial audit trails when catalog products undergo price revisions or are archived post-purchase.
  • Framework Overhead: Modern enterprise frameworks (e.g., Spring Boot) introduce considerable memory footprints, slow startup times, and complex dependency graphs. Demonstrating systems programming mastery requires building these mechanisms from foundational computer science primitives.

2.2 Problem Statement

Traditional capstone projects often either rely heavily on heavy-weight framework conventions that obscure foundational architectural concepts, or produce trivial mock systems lacking real-world concurrency control, multi-vendor isolation, and transactional ACID guarantees.

The objective of this project is to construct a production-ready, zero-framework, multi-vendor e-commerce marketplace that coordinates independent Customer, Vendor, and Administrator workflows; guarantees strict ACID transaction semantics during order placement and stock deduction; and delivers commercial-grade performance.

4. Software Requirements Specification (SRS)

4.1 Tri-Role Functional Architecture

  • Customer: Catalog discovery, faceted search (by category, brand, price range), multi-image carousel, persistent database-backed cart, 1-click wishlist, promo coupon validation, transactional checkout, order cancellation with inventory replenishment, and live notification feed.
  • Vendor: Sales KPI dashboard (total products, active orders, gross revenue), full catalog CRUD with image URLs, stock quantity updates, order line item fulfillment status progression.
  • Administrator: Platform KPI metrics (customers, active vendors, catalog count, platform GMV), user status toggles (Active, Inactive, Banned), vendor approval/suspension workflow, category & brand registry management, and global order audit.

4.2 Non-Functional Requirements (NFR)

  • ACID Consistency: All multi-item checkout operations must execute within a single database transaction boundary. In the event of stock insufficiency or database failure, all modifications must be rolled back completely.
  • Sub-50ms Latency: REST API endpoints respond in under 50ms for indexed database queries. Static SPA assets serve with sub-millisecond overhead.
  • Connection Recycling: A custom connection pool with dynamic proxy interception eliminates TCP socket creation delays.
  • Security: Parameterized PreparedStatements eliminate SQL injection across all queries; token-based Bearer authentication governs role boundaries.

5. System Architecture & High-Level Design

BuyIt adopts a Three-Tier Layered Architecture ensuring loose coupling between presentation, application logic, and relational persistence:

Three-Tier Decoupling:
Tier 1 (Presentation): React 18 Single-Page Application (SPA) + Interactive Terminal CLI.
Tier 2 (Application): Pure Java SE HttpServer with custom multi-threaded router, session token store, and business services.
Tier 3 (Data): Cloud PostgreSQL (Supabase) with custom proxy-managed connection pool.

6. Object-Oriented Analysis & Design (OOAD)

The project provides a textbook demonstration of core Object-Oriented Programming (OOP) principles:

  • Inheritance: Abstract base class model.User is extended by concrete subclasses model.Customer, model.VendorUser, and model.Admin.
  • Polymorphism: UserService maps database rows dynamically into polymorphic User instances based on the discriminator column role.
  • Encapsulation: Domain entities (such as Product and Order) maintain private fields with validated accessor methods and business calculations (e.g. getFinalPrice()).
  • Abstraction: Service layers (e.g. OrderService, ProductService) encapsulate complex SQL transactions away from controllers.

9. Transactional Concurrency & ACID Safety

Order placement represents the most critical transaction in e-commerce. BuyIt guarantees strict ACID (Atomicity, Consistency, Isolation, Durability) compliance via pure JDBC:

// Transactional Boundary Management (OrderService.java)
Connection conn = Database.getConnection();
try {
    conn.setAutoCommit(false); // Begin ACID Transaction

    // 1. Verify stock sufficiency for all items
    for (OrderItem item : items) {
        if (!productService.hasSufficientStock(conn, item.getProductId(), item.getQuantity())) {
            throw new SQLException("Insufficient stock for: " + item.getProductName());
        }
    }

    // 2. Insert master order & batch insert order items
    int orderId = insertOrder(conn, customerId, totalAmount, finalAmount);
    insertOrderItemsBatch(conn, orderId, items);

    // 3. Atomically decrement stock with database-level row guard
    for (OrderItem item : items) {
        productService.reduceStock(conn, item.getProductId(), item.getQuantity());
    }

    // 4. Insert payment ledger entry
    insertPaymentRecord(conn, orderId, paymentMethod, finalAmount);

    conn.commit(); // Commit All Operations Atomically
} catch (Exception e) {
    if (conn != null) conn.rollback(); // Rollback All on Failure
    throw e;
} finally {
    if (conn != null) {
        conn.setAutoCommit(true);
        conn.close(); // Recycle to Pool
    }
}

11. Security Architecture & Governance

  • Bearer Token Authorization: Authenticated sessions are managed via ConcurrentHashMap<String, Integer> mapping randomly generated UUIDs to active user IDs.
  • Role-Based Access Control (RBAC): Endpoints inspect the user's role before permitting action execution. Unauthorized attempts receive 401 Unauthorized or 403 Forbidden.
  • SQL Injection Immunity: All SQL queries across all 12 services utilize parameterized PreparedStatement instances. String concatenation of user inputs into SQL is strictly prohibited.

15. Engineering Challenges, Future Roadmap & Conclusion

15.1 Key Challenges Solved

  • Framework-free REST routing: Implemented path matching and JSON marshalling using standard JDK classes.
  • Dynamic Proxy Connection Pool: Intercepted Connection.close() calls using Java reflection proxies to recycle connections seamlessly.
  • Inventory Race Conditions: Enforced atomic decrements at the database row level to prevent overselling.

15.2 Conclusion

The BuyIt Multi-Vendor E-Commerce Marketplace demonstrates that scalable, production-grade enterprise systems can be engineered with elegance, high performance, and zero framework bloat.
